# tob

複数まとめて型指定する。ネスト構造も可能。

一箇所でも型不一致なら即時例外発生させる。なぜなら型の不一致はコンパイル言語ならば実行前に停止すべき事だから。JSなどのインタプリタ言語では実行時エラーになるが、それを事前に制御可能かつ原因箇所と理由が特定可能な状態にするため即時例外発生させるようにした。

尚、対象は型だけであり値の妥当性（バリデーション）は対象外とする。バリデーションの場合は例外発生させず問題の対象と理由を示す適切なメッセージが欲しくなる。その場合は例外発生とは違う実行結果にする必要がある。当然、バリデーション処理内容の定義も必要になる。それを短く記述できる構文も考えねばならない。

## 型指定

```javascript
const o = tob({
    bln: Boolean,
    num: Number,
    int: Number.isSafeInteger,
    int: Number.isInteger,
    fin: Number.isFinite,
    str: String,
    big: BigInt,
    sym: Symbol,
    fn : Function, // tis.fn(v)
    pob: Object,
    ary: Array,
    ins: Map, // tis.cls(v)
//    cls: Map,
//    ins: new Map(),
    nest: { // {}の中に一つ以上のプロパティが存在すればネスト構造の指定である。一つもなければObject型指定である。
        bln: Boolean,
        obj: Object,
    }
});
```

関数指定子は冗長だ。定数指定子でも型指定できるようにしよう。以下のように。中には定数指定子でないと指定できない型もある。配列の要素型指定がそれだ。

```javascript
const o = tob({
    bln: false,
    int: 0, // Number.isSafeInteger
    flt: .5, // Number.isFinite
//    num: Number,
//    int: Number.isSafeInteger,
//    int: Number.isInteger,
//    fin: Number.isFinite,
    str: '',
    big: 0n,
    sym: Symbol(),
    fn : ()=>{},
//    ins: new Map(),
//    cls: Map,
//    ins: new Map(),
    pob: {}, // {}の中に一つ以上のプロパティが存在すればネスト構造の指定である。一つもなければObject型指定である。
    nest: { // {}の中に一つ以上のプロパティが存在すればネスト構造の指定である。一つもなければObject型指定である。
        bln: false,
        obj: {},
    }
    ary: [], // tis.ary(v)
    ary: [false], // tis.ary(v, tis.bln)
    ary: [0],
    ary: [''],
    ary: [0n],
    ary: [Symbol],
    ary: [()=>{}],
    ary: [Map],
    ary: [{}],
    ary: [[]],
});
```
```javascript
const o = tob({
    cls: tob.cls(MyCls), // classを変数にしたい時はレアケースなので専用APIでのみ可能とする。代わりに`ins:MyClas`のようにしてインスタンス型であることをクラス指定で示せるようにする。
});
```

tobはよくあるoptions引数の型判定に使える。

```
function api(options) {
    tob({...})(options); // 一つでも異常があれば例外発生する。
}
```

但し判定内容は型だけであり値の妥当性は対象外のため、それは別途実装する必要があるだろう。

型|NaN|Infinity|少数|MAX_VALUE|SAFE|問題
--|---|--------|----|---------|----|----
Number|⭕|⭕|⭕|⭕|⭕|算術式破綻可能性あり
Number.isFinite|❌|❌|⭕|⭕|⭕|浮動小数点数誤差あり
Number.isInteger|❌|❌|❌|⭕|⭕|最小単位1超過
Number.isSafeInteger|❌|❌|❌|❌|⭕|`2**53`境界

Number型は型破綻している。`NaN * 3`のようにすると常に`NaN`を返却し実質機能しない。計算を停止させないことでそれ以外の計算結果は得られるようにしたい時に意義がある。しかしリアルタイムに問題箇所を特定することを困難にさせるバグの温床だ。±Infinityも同様。MAX_VALUEは最小単位1を超過してしまい通常の算術計算が破綻する。浮動小数点数は0.5,0.125など2のマイナスN乗でないと誤差が生じる。故に誤差なく算術計算が成立するNumber.isSafeInteger以外は到底同じ型として判定すべきでない致命的な問題を抱えている。

`fin: .5`について。Finite型のことだ。不動少数点数を含むNumber型である。なぜ定数指定子が`.5`(または`0.5`)なのか。それは浮動小数点数が2のマイナスN乗値のみ誤差なく指定できるから。例えば0.5,0.25,0.125などだけは誤差なく===で比較できるから。逆に`0.1`などの数は誤差が発生してしまい===判定できない。そして`.5`こそ尤も短く書ける誤差のない浮動小数点数のリテラル値である。だから`.5`をFinite型の定数指定子にした。

最も安全なNumber.isSafeIntegerにもC/C++でいうオーバーフローが発生しない問題がある。そもそも2**53境界という不自然な範囲しか扱えないこと自体も問題だが、更に致命的なのがオーバーフローもエラーにもならず、SAFE値を超過すると最低間値1を超過した誤差のある整数になってしまうという点だ。そんな状態でエラーにもならずオーバーフローもされずに処理が継続されてしまう。故に例外発生させるべきだ。SAFEの境界値 2**53 で。

## 代入

```javascript
const o = tob({...});
o.bln = false;  // 代入成功
o.bln = 0;      // TypeError: 期待する型と一致しません。
o.notExist = 0; // ReferenceError: 未定義のプロパティが参照されました。JS標準挙動であるundefined返却し継続すれば不具合箇所の特定が困難になるため当該箇所で例外発生させました。
o(someObj);     // 一括代入（一箇所でも上記問題があれば順次例外発生させる）
```

# tay

tayはtobの配列版。以下のようにする。

```javascript
const a = tay([
    Boolean,
    Number,
    Number.isSafeInteger,
    ...
]);
a[0] = false;      // 代入成功
a[0] = 0;          // TypeError: 期待する型と一致しません。
a[Infinity] = 0;   // RangeError: 添字範囲超過。
a['notExist'] = 0; // ReferenceError: 未定義のプロパティが参照されました。JS標準挙動であるundefined返却し継続すれば不具合箇所の特定が困難になるため当該箇所で例外発生させました。
a(someAry);        // 一括代入（一箇所でも上記問題があれば順次例外発生させる）
```

tayは関数の引数型チェックにも使える。

```javascript
function fn(...args) {
    const a = tay([
        Boolean,
        Number,
        Number.isSafeInteger,
        ...
    ]);
    a(args); // 関数fnの引数型判定。一つでも異常があれば例外発生する。
}
```
```javascript
function fn(...args) {
    tay([
        Boolean,
        Number,
        Number.isSafeInteger,
        ...
    ])(args); // 関数fnの引数型判定。一つでも異常があれば例外発生する。
}
```

### 残余引数

```
sort(3, 2, 6, -1); // 引数が可変長である
```

```
function sort(...args) {

```

# Nullable

実際の案件ではNullableな型を指定したい時もある。

Reference型はすべてNullableにすることも可能だが、非Nullableに限定したい場合もある。

同様にNumber型であればNaNableの是非についても考慮が必要だ。だがこちらは単純に`Number`と型指定した時だけNaN,Infinity,SAFE超過値を許容できるようにしよう。できれば使うべきでない型として。代わりに`0`や`.5`を使うべきだ。

# 初期値

初期値をどうするか。Primitive型はデフォルト値を指定できるだろう。

型|初期値
--|------
Boolean|false
Number|0
BigInt|0n
String|''
Symbol|Symbol()

だがReference型はどうか。

型|初期値
--|------
Object|{}
Array|[]
Function|null
Instance|null

仮に上記にするならばNullableについて考慮せねばならない。もしNullableならば初期値をnullにすべき場合もありうる。もし非NullableならFunctionやInstanceはどうしたらいいのか。Instanceに関しては指定されたコンストラクタ関数の引数なし版で`new`すれば良い。いずれにせよ以下のパターンがありうる。

1. Nullable（nullを許容する）
2. 非Nullable（nullを禁止する）

基本的には非Nullableにしておこう。それはPrimitiveは当然、Function、Instance共に。理由はNULL安全のためだ。

となるとNullableにするための記法を考える必要がある。以下のように配列化して指定する。その場合その配列は要素が二個以上あり二番目の要素がnullであること。これで配列型指定と区別できるはず。

```javascript
const o = tob({
    bln: [Boolean, null],
    num: [Number, null],
    int: [Number.isSafeInteger, null],
    int: [Number.isInteger, null],
    fin: [Number.isFinite, null],
    str: [String, null],
    big: [BigInt, null],
    sym: [Symbol, null],
    fn : [Function, null], // tis.fn(v)
    pob: [Object, null],
    ary: [Array, null],
    ins: [Map, null], // tis.cls(v)
//    cls: Map,
//    ins: new Map(),
    nest: [{ // {}の中に一つ以上のプロパティが存在すればネスト構造の指定である。一つもなければObject型指定である。
        bln: [Boolean, null],
        obj: [Object, null],
    }, null]
});
```

```javascript
const o = tob({
    bln: [false,null],
    int: [0,null], // Number.isSafeInteger
//    num: Number,
//    int: Number.isSafeInteger,
//    int: Number.isInteger,
//    fin: Number.isFinite,
    str: ['',null],
    big: [0n,null],
    sym: [Symbol(),null],
    fn : [()=>{},null],
//    ins: [new Map(),null],
//    cls: [Map,null],
//    ins: [new Map(),null],
    pob: [{},null], // {}の中に一つ以上のプロパティが存在すればネスト構造の指定である。一つもなければObject型指定である。
    ary: [[],null], // tis.ary(v)
    ary: [[false],null], // tis.ary(v, tis.bln)
    ary: [[0],null],
    ary: [[''],null],
    ary: [[0n],null],
    ary: [[Symbol],null],
    ary: [[()=>{}],null],
    ary: [[Map],null],
    ary: [[{}],null],
    ary: [[[]],null],
    ary: [[0],null],
    ary: [[0],null],
});
```
```javascript
const o = tob({
    cls: tob.cls(MyCls, null), // classを変数にしたい時はレアケースなので専用APIでのみ可能とする。代わりに`ins:MyClas`のようにしてインスタンス型であることをクラス指定で示せるようにする。
});
```

あるいはReference型は基本的にNullableにするか？　だが最終的にはnullだと処理の継続が不可能になるか、その時用の処理を実行させる必要があるはずだ。ならばReference型において必要なのはNullableか否かのフラグではなく、初期値を生成するコールバック関数かもしれない。ただ、それが非同期処理を含む外部APIを必要とする場合、一般化することは言語仕様上困難だ。レアケースにあわせて毎回await呼び出しすると通常時の使い勝手が悪化するから。

記法に関しては`tob({i?:0})`のように名前の末尾に`?`を付与することで指定できないかと考えたがJS言語仕様上不可能だった。

```sh
$ bun repl
Welcome to Bun v1.4.2
❯ let o = {k?:0};
SyntaxError: Unexpected token '?'. Expected a ':' following the property name 'k'.
```

仮にできたとしても`tay([0])`のように名前がない配列版の場合は指定できない。故にどのみちこの記法は使えない。

同様にNumberの詳細型に関してはNaN, Inifinity, -Infinity, SAFE超過の数を対象とするか否かの判定も必要だ。基本的には禁止にすべきだろう。つまりintだろうがfinだろうがSAFE超過した数は対象外であり例外発生させるべきだ。SAFE超過値は1単位を維持できないため数として破綻しているからだ。

それらを使いたいなら単純に`Number`と型指定すれば良いことにしよう。一々`[0,NaN,Inifinity,-Infinity,Number.MAX_VALUE]`のように指定させるのはバカバカしい。破綻した型のために長ったらしい指定を用意し、それを解析する実装まで用意するなど馬鹿げている。

ちなみに`undefined`は全面的に禁止する。理由は存在しないプロパティ参照時の返却値と区別がつかないから。

# 初期値の指定

型だけでなく実際の値を代入したいこともあるだろう。以下のように。

```javascript
const o = tob({
    num: [Number, 123],
});
```

しかし配列、第二引数は色々とややこしい。配列型指定と区別がつきづらいし、Nullable指定の話もある。Nullable指定によるnullなのか、それとも初期値としてのnullなのか。どうやって区別をつけたらいい？

```javascript
const o = tob({
    ins: [Map, null], // このnullはNullableなのか、初期値がnullなのか区別不能！
});
```

Nullableは基本的に特殊形とする。故に冗長な記法によって初期値nullと区別するようにする。

```javascript
const o = tob({
    ins: tob.nul(Map), // Nullableにしたい時は`tob.nul()`を使うことにする
});
```
```javascript
const o = tob({
    ins: tob.nul(Map,null), // 初期値は第二引数で指定する
});
```
```javascript
const o = tob({
    ins: tob.nul([0],[123]), // Array?<Integer>型。初期値[123]
});
```

ところでNullable指定、初期値指定、初期値関数指定における略記について。

```javascript
const o = tob({
    ins: tob.nul(Map,null), // Map?型。初期値null
});
```

上記の場合、`null`が二箇所もある。略記できるはずだ。もし`tob.nul()`があればNullableなので、初期値が省略された時は`null`にするか。あるいは`new Map()`などデフォルトコンストラクタにするか。

```javascript
const o = tob({
    ins: Map,                    // 初期値null/new Map()どちらにすべき？
    ins: [Map, null],            // 型はNullableにすべき？
    ins: [Map, new Map()],       // 型はNullableにすべき？
    ins: tob.nul(Map),           // 初期値null/new Map()どちらにすべき？
    ins: tob.nul(Map,null),      // 冗長だが明示的
    ins: tob.nul(Map,new Map()), // 冗長だが明示的
});
```

基本的に非Nullable型にすべき。この思想を貫くならば`[Map, null]`の時は初期値で`null`が設定されることになる。`tob.nul()`指定されない限りは非Nullableだ。なのに`null`が初期値として代入されたら型違反である。

ということはNullableで初期値nullにしたい場合は`tob.nul(Map, null)`という重複記述しかありえないことになってしまう。もし`tob.nul(Map)`なら初期値は`new Map()`になる。なぜなら基本は非Nullableだから。しかしそれはパフォーマンス的に如何なものか。特に気がかりなのが初期化の段階ではnewしたくないがためにNullableにせざるを得ないが、初期化以降は非Nullableにしたいというケースである。

PrimitiveとReferenceではNullableにする意味が違う。PrimitiveにおいてNullableにする意味は、nullの値によって「存在しないこと」などを意味する用途だ。しかしReferenceにおいては存在しないと後続の処理に支障を来すため実質例外発生すべきと言える。更に初期化しインスタンス生成するための引数が確定していない可能性もある。

* Reference型（Function,Class,Instance（ObjectやArrayは対象外））のみ初期値は
	* 全て
		* `null`である
		* デフォルトコンストラクタである
	* 指定したプロパティだけ
		* `null`である
		* デフォルトコンストラクタである
		* 指定値である
* Primitive型（とObjectやArray）のみ初期値は
	* 全て
		* 型に基づくデフォルト値である（`false`,`0`,`0n`,`''`,`Symbol()`,`{}`,`[]`）
	* 指定したプロパティだけ
		* `null`である
		* 指定値である

上記のようなパターンがある。Primitiveは比較的簡単だ。但しObjectやArrayは中間的であり微妙。そしてReferenceはパターンが多いため、どうすべきか明確に指定が必要だ。

NULL安全にするなら非Nullableにすべきだ。しかし非Nullableにするためには初期値を確定させねばならず、その確定処理にはasync関数の実行が必要な場合もありうる。sync関数との呼び分けには呼び出し元の文脈レベルで変えねばならず単一コードで記述できない。これが最大の問題である。

## Primitive

```javascript
const o = tob({
    bln: Boolean,				// 初期値=false
    bln: false,
    bln: tob.nul(Boolean),		// 初期値=null
    bln: tob.nul(false),
    bln: [Boolean, true],		// 初期値=true（第二要素）
    bln: [false, true],
    bln: [false, null],			// TypeError: 値が期待する型と一致しません
    bln: tob.nul(false, null),	// 初期値=第二引数値
    bln: tob.nul(Boolean, true),
    bln: tob.nul(false, true),
});
```

### Number

```javascript
const o = tob({
    num: Number,				// 初期値=0
    num: Number.isSafeInteger,
    num: Number.isInteger,
    num: Number.isFinite,
    num: 0,						// 初期値=0。Number.isSafeInteger
    num: .5,					// 初期値=0。Number.isFinite
    num: tob.nul(Number),		// 初期値=null
    num: tob.nul(0),
    num: [Number, 123],			// 初期値=123（第二要素）
    num: [0, 123],
    num: [.5, 123],
    num: [0, null],				// TypeError: 値が期待する型と一致しません
    num: [.5, null],			// TypeError: 値が期待する型と一致しません
    num: [0, 0.1],				// TypeError: 値が期待する型と一致しません
    num: [0, NaN],				// TypeError: 値が期待する型と一致しません
    num: [0, Infinity],			// TypeError: 値が期待する型と一致しません
    num: [0, Number.MAX_VALUE],	// TypeError: 値が期待する型と一致しません
    num: [.5, Number.MAX_VALUE],// TypeError: 値が期待する型と一致しません
    num: [0, Number.MAX_SAFE_INTEGER+1],	// TypeError: 値が期待する型と一致しません
    num: [.5, Number.MAX_SAFE_INTEGER+1],	// TypeError: 値が期待する型と一致しません
    num: tob.nul(Number, 123),	// 初期値=第二引数値
    num: tob.nul(0, 123),
    num: tob.nul(0, null),
});
```

Number型ならTypeErrorにならないがNumber.isSafeInteger,Number.isInteger,Number.isFinite,ならエラーになる。尚、Number.isIntegerを使いたいケースはレアケースだろうから対応しなくてもいいくらいだ。

尚、以下のような境界値も型指定できるようにしてもよいが。結局はSafeIntegerに値の妥当性確認をするものである。但し例外発生させるかオーバーフローさせるか上限値停止させるかを決定せねばならない。

```javascript
const o = tob({
    u8:    8,
    s8:   -8,
    u16:  16,
    s16: -16,
    u32:  32,
    s32: -32,
});
```

超過時の処理を指定する必要があるなら数のリテラル値だけでは指定不能だ。型の名前を考えたほうがいい。`s`は`i`のほうが良いかもしれないが。

```javascript
const o = tob({
    u8:  tob.u8,
    s8:  tob.s8,
    u16: tob.u16,
    s16: tob.s16,
    u32: tob.u32,
    s32: tob.s32,
});
```

超過時の処理を明示するなら以下。

```javascript
const o = tob({
    u8:  tob.u8.throw|flow|stop,
    s8:  tob.s8.throw|flow|stop,
    u16: tob.u16.throw|flow|stop,
    s16: tob.s16.throw|flow|stop,
    u32: tob.u32.throw|flow|stop,
    s32: tob.s32.throw|flow|stop,
});
```
```javascript
RangeError: 範囲超過。u|s 8|16|32 の範囲を超過しました。
```

### Object

```javascript
const o = tob({
    obj: Object,				// 初期値={}
    obj: {},
    obj: tob.nul(Object),		// 初期値=null
    obj: tob.nul({}),
    obj: [Object, {k:0}],		// 初期値={k:0}（第二要素）
    obj: [{}, {k:0}],
    obj: [{}, null],			// TypeError: 値が期待する型と一致しません
    obj: tob.nul(Object, {k:0}),// 初期値=第二引数値
    obj: tob.nul({}, {k:0}),
    obj: tob.nul({}, null),
});
```

ネスト構造を指定する時は以下。無限に再帰的に掘り下げることができる。

```javascript
const o = tob({
    obj: {sub:{k:Number}},						// 初期値={sub:{k:0}}
    obj: tob.nul({sub:{k:Number}}),				// 初期値=null
    obj: [{sub:{k:Number}}, {sub:{k:123}}],		// 初期値={sub:{k:123}}
    obj: [{sub:{k:Number}}, null],				// TypeError: 値が期待する型と一致しません
    obj: tob.nul({sub:{k:Number}}, {sub:{k:0}}),// 初期値=第二引数値
    obj: tob.nul({sub:{k:Number}}, null),
});
```

ネスト構造の時は指定されたプロパティ名が存在することが必須条件になる。だが、指定されていないプロパティ名についてはどうするか。また、指定されたプロパティ名がいずれかの場合であれば良いなど複雑なパターン指定もありえる。JSON Schemaのように。但しそうした複雑なパターンは対象外とする。基本的に`tob`や`tay`は指定したオブジェクト形式をそのまま返却する。しかもそのオブジェクトから新しいプロパティを生やしたら例外発生するようにする。Proxyを使って。つまり存在しないプロパティ参照時も同じ例外発生させる。これにてundefinedを返却して継続するようなバグの温床を徹底排除する。

### Array

```javascript
const o = tob({
    ary: Array,					// 初期値=[]
    ary: [],
    ary: tob.nul(Array),		// 初期値=null
    ary: tob.nul([0,1]),
    ary: [Array, [0,1]],		// 初期値=[0,1]（第二要素）
    ary: [[], [0,1]],
    ary: [[], null],			// TypeError: 値が期待する型と一致しません
    ary: tob.nul(Array, [0,1]),	// 初期値=第二引数値
    ary: tob.nul(0, [0,1]),
    ary: tob.nul(0, null),
});
```
